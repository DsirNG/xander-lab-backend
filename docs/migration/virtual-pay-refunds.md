# 小程序订单与按积分比例退款

## 规则

- “我的 → 我的订单”、套餐购买页均有入口。列表按当前登录用户隔离，游标分页每页 20 条。
- 普通微信支付：只允许在支付后 7 × 24 小时内申请。以 `query_order.order.paid_time` 秒级 UTC 时间为准，恰好到期即拒绝，不使用本地发货时间推算。不完整/未来支付时间不放行。
- 套餐和积分卡统一：`floor(原订单实付分 × 该订单未使用毫积分 ÷ 该订单原始毫积分)`。低于 1 分不退款。套餐成功退款后终止该订单会员，之后购买的新套餐不受影响。
- 申请前预览金额，提交时再计算并校验用户确认金额。金额改变不自动退另一金额。
- 原订单全部未使用积分先原子冻结；成功回收、明确失败恢复。过期套餐积分恢复后仍按原到期时间失效。退款冻结/恢复不计入今日消费。
- 每笔订单一次剩余权益退款。失败记录保留并转人工处理，不通过换退款号自动重试。平台返回受理不等于到账。
- Apple 支付由用户向 Apple 申请，Apple 决定结果；应用不能代替 Apple 主动退钱。收到并核实平台全额退款后回收尚存权益。已消耗部分保留消费审计，不扣其他订单积分。
- 历史永久积分没有按订单归属记录，不从总余额推算退款。外部部分退款、账号合并后的原订单及无法明确核实的退款需人工核对。不得凭通知正文或状态 5 直接认定完成。

## 数据归属与接口

Core 独占积分批次与 `payment_refund_hold`。Payment 独占 `virtual_pay_refund`，通过服务鉴权的 `POST /internal/v1/payment/points/refund` 调用 quote/reserve/complete/release；不跨 D1 查询。

- `GET /api/virtual-pay/orders?before=<id>`：当前用户订单。
- `GET /api/virtual-pay/orders/{id}/refund-quote`：可退款金额、原因、原始/剩余积分、截止时间。
- `POST /api/virtual-pay/orders/{id}/refund`：`{expectedAmount: 整数分}`，金额不信任客户端，仅用于确认比对。
- `GET /api/virtual-pay/orders/{id}/refund-status`：核对并返回持久化状态。
- `POST /api/virtual-pay/notify`：既有验签入口接收退款通知。先验证通知订单身份，再服务端查单核实资金变化。

状态 PREPARING → SUBMITTING → PROCESSING → SUCCEEDED/FAILED；不能确定的拒绝进入 REVIEW。超时保持 SUBMITTING，禁止无证据重发。每 5 分钟最多检查 20 笔，检查后轮转排序，避免某笔异常长期占据首批。原单余额、退款单类型及结果均匹配才更新权益；用户退款完成状态 8 可用于核对，状态 5 不作通用成功依据。

永久购买积分按套餐积分之后、购买批次 FIFO 消耗；迁移前余额保持未归属永久余额。正在冻结退款时禁止迁出账户余额，避免合并与恢复竞争。

## 发布与验证

1. 备份 Core / Payment 数据库，先应用 Core `0011_payment_refunds.sql` 和 Payment `0005_order_refunds.sql`。SQLite 中文说明使用 SQL 注释，不使用 MySQL COMMENT 语法。
2. 发布 Core，再 Payment（保留服务绑定、消息 Token 和 AppKey，启用配置中的每 5 分钟 cron），再 Gateway，最后小程序。关闭购买商品不妨碍已有退款查单。
3. 真实上线前在已发布的低价商品上验证：支付、发货、消耗部分积分、退款预览、申请、冻结、通知/查单、到账与积分回收。验证原支付时间、`order_type`、`left_fee` 与退款单号的真实返回；协议缺失时保持待核对，不伪造到账。
4. Apple 需单独进行平台允许的退款验证。自动化测试仅使用本地 SQLite 和模拟支付接口，不产生真实扣款/退款。

核对 REVIEW 时查微信 MP 原支付与退款记录、Core 冻结记录。先确认资金最终结果，再处理；不能删除退款行后重试，也不能仅根据 HTTP 超时恢复积分。历史与外部部分退款本版本不自动估算权益。
