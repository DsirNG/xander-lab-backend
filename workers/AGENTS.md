# Cloudflare Workers workspace rules

This directory is the TypeScript Cloudflare Workers target. The Java/Spring
Boot implementation remains authoritative until a service is migrated and
cut over.

- Keep each deployable service in `services/<service>` with its own Wrangler
  config, D1 binding, migrations, and deployment command.
- Keep service code in Controller → Service → Interface → Mapper layers:
  Controllers parse HTTP input and shape responses; Services contain use-case
  logic; Interfaces define persistence and cross-service ports; Mappers contain
  D1 queries and remote-contract adapters. Keep route entry points thin.
- A service owns its D1 data. Never query another service's D1 or add a
  cross-service foreign key. Use versioned service-authenticated HTTP
  contracts and idempotent requests/events across service boundaries. Use
  same-account service bindings for internal calls; retain HTTPS service URL
  fallbacks when services are intentionally split across Cloudflare accounts.
- Use Workers Web APIs. Do not assume a Node.js filesystem, TCP socket, or JVM
  runtime exists inside a Worker.
- Keep binary files and large generated content in Alibaba OSS. D1 stores
  ownership, object keys, metadata, and lifecycle state only.
- Never commit `.dev.vars`, production credentials, account IDs, or live D1
  identifiers. Local dev secrets are generated by `pnpm dev` and removed when
  the local stack shuts down.
- Public API errors preserve `{ code, message, data }`; HTTP status must match
  the error code. Health probes are infrastructure responses, not business
  APIs.
- The Gateway route manifest is generated from the Java route inventory and
  explicit owner mapping. Internal-only routes and Studio/Components routes
  must not be exposed through the public Gateway.
- Run `pnpm check` after Worker changes. Use `pnpm dev` to start the local
  stack; it uses Wrangler's local runtime and local D1 emulation.

The Cloudflare migration plan is in `../docs/migration/cloudflare-workers-d1-plan.md`.
